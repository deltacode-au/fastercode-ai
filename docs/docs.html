fastercode

Reference documentation. fastercode.ai is the proof layer for AI-written code. Independently verify agent-generated rewrites against evidence you choose. 

Use fastercode.ai directly from supported coding agents through MCP or use the Python API for manual control.

New here? Start with Agent quickstart, or see what fastercode is.

01Agent quickstart

1.1 · Setup

fastercode requires Python 3.10 or newer. 

shell 
pip install fastercode-ai

Register it with Claude Code (Only Claude Code is supported in V0.2.1):

shell 
claude mcp add fastercode -- python -m fastercode.mcp_server

Or using Claude Code's own MCP config file. The installed fastercode-mcp console script is equivalent to python -m fastercode.mcp_server, use whichever Claude Code resolves more reliably.

json 
{
  "mcpServers": {
    "fastercode": {
      "command": "python",
      "args": ["-m", "fastercode.mcp_server"]
    }
  }
}

Paths are resolved against the server's working directory, which is whatever your harness launched it in. Pass absolute paths unless you know the server started in your project root.

1.2 · The workflow

The agent calls analyse_function first, which reports the recording strategies that actually apply to your function. It should then ask you which one to use rather than choosing silently: the strategy determines what the report is evidence of.

StrategyMeasures againstWhen it applies
entryyour script, replayed end to endPreferred — when a function in your file calls the target.
testthe calls your own test makesA test exercises the target. Given as path::test_name.
inputscalls the agent inventsNothing else is available. Weakest evidence — a good agent will say so.

Then optimise_function swaps in each candidate, replays the recorded calls, and keeps the best one that is both correct and better. A candidate whose outputs differ from the original is rejected and that outcome is the point of the tool, not a failure to hide. If nothing wins, your original is left exactly as it was.

1.3 · What you can ask for

Four things are yours to decide, and it is worth saying them out loud when you make the request:

SettingValuesSay something like
objectivespeed, loc, memory"make it faster" · "make it shorter" · "cut its memory use"
recordingentry, test, inputs"measure it against my real pipeline" · "use my test as the evidence"
constraintsmax or max_relative per metric"faster, but don't use more than 1.2x the memory"
modeindependent, iterative"judge each against the original" · "keep building on the best one"

Constraints work exactly as they do in the Python API, bounds apply to the two metrics you did not pick as the objective. A candidate that is correct and meets the objective but breaks a constraint is recorded as constraint_violated rather than counted as a win.

1.4 · The tools

ToolWhat it doesTouches your code?
analyse_functionThe function's source and parameters, which recording strategies apply, and any earlier runs whose report could be read instead of re-running.No
optimise_functionMeasures the candidates and applies the best correct improvement.Yes
list_runsRuns already on disk, newest first, with the path to each report.No
get_runA run's full measurements: every attempt, the code that ran, its sha256, the outputs it produced.No
swap_versionWrites a specific recorded version back into the file. For reverting to another measured version, not normal use.Yes

1.5 · What gets written

Everything lands under .fastercode/<hash>/optimise_runs/<timestamp>/: a report.pdf, the full measurements in json/optimise.json, and backups/ holding the exact code executed for each try. You can also ask your Agent where the results were saved and a link to the directory. 

02How it works

An overview of fastercode's workflow and more detailed features are summarised below, in addition to the practical implementation of the core principles: Privacy and verification. 

01 Overview ~6 min read

The overall process is designed to be easy, deterministic and repeatable. It starts with the user selecting either a function or a block of code through the decorator or by defining a job using a .YAML file. 

The user simply runs the script as it used to work, that's where fastercode takes over. Rather than executing the script or program once, it iterates as many times as the user specifies with hot-swapped LLM suggestions. If your code originally took 30s to complete and you've defined 3 retries in fastercode, it will now take approximately 120s to complete plus any API response times. At the end of the process, you will have optimised code that meets your defined constraints, copies of the target script with swapped-in code, a PDF report summarising the results and raw JSON files containing metadata. 

Users are able to define what they are optimising for, either speed, loc or peak memory usage. They can also define two types of constraints: Performance constraints and/or code constraints. 

Performance constraints are the same as the objectives: speed, loc or peak memory usage and are expressed as absolute values or multiples of the baseline test results. 

Code constraints are either subsets of code or variables inside the target that must remain unchanged in the suggested solutions. 

Decorator

Add @optimise.track straight onto a function in your own source and call optimise() yourself. This is the simplest way when you're editing the script or working inside a notebook. 

Decorated:

python 
from fastercode import refactor

optimise = refactor()


@optimise.track
def sum_of_squares(values):
    total = 0
    for v in values:
        total += v * v
    return total

sum_of_squares([1, 2, 3, 4, 5])
optimise.optimise(sum_of_squares, tries=5)

Job YAML

Write a YAML file naming a script, an entry_point, and the functions to track by string, and let run_job() dynamically patch them at runtime. Both paths drive the exact same underlying engine; only how the target gets wired up differs. The target script still needs to be called from wherever run_job() is declared.  

 Same function, left completely undecorated:

python 
# target.py — no refactor import, no decorators
def sum_of_squares(values):
    total = 0
    for v in values:
        total += v * v
    return total

def run_pipeline():
    sum_of_squares([1, 2, 3, 4, 5])

if __name__ == "__main__":
    run_pipeline()

...targeted by name in a job YAML instead — the full field surface, not just the minimum needed to wire it up:

yaml 
name: sum_of_squares_job
language: python

api:
  provider: openai
  key: ${OPENAI_API_KEY}
  model: gpt-4o

script: target.py
entry_point: run_pipeline
objective: speed
constraints:
  memory:
    max_relative: 1.2

targets:
  - name: sum_of_squares
    keep:
      variables: ["total"]

post_run:
  - action: optimise
    target: sum_of_squares
    tries: 5

Then run it:

python 
from fastercode import refactor

optimise = refactor()
optimise.run_job("job.yaml")

Performance constraints

objective picks the one metric being minimized: "speed", "loc", or "memory". constraints= caps the two metrics you didn't pick — an absolute ceiling or a multiple of your recorded baseline; a candidate that's correct and would otherwise win still gets turned down, marked constraint_violated, if it breaks one. Every try lands in exactly one of four conditions: accepted, rejected (wrong output, or just not better), constraint_violated, or timeout.

Code constraints

optimise.keep(func, variables=None, lines=None) is different in kind: it doesn't cap a number, it pins down which local variables and/or source lines must survive the refactor untouched, so you control what code the LLM is allowed to touch, not just how fast the result runs. Breaking a code constraint is enforced differently, too — it aborts that candidate's swap outright, surfacing as a plain rejected with an error message, not the dedicated constraint_violated condition reserved for performance constraints.

python 
optimise = refactor(
    objective="speed",
    constraints={"memory": {"max_relative": 1.2}},  # performance constraint
)


@optimise.track
def sum_of_squares(values):
    total = 0
    for v in values:
        total += v * v
    return total


optimise.keep(sum_of_squares, variables=["total"])  # code constraint

sum_of_squares([1, 2, 3, 4, 5])
result = optimise.optimise(sum_of_squares, tries=5)

The verification framework

Correctness checking is deterministic and runs entirely on your own machine — no network call, and independent of whichever LLM produced the candidate. Every historically recorded call gets replayed and its output compared by strict equality before a candidate's speed, LOC, or memory is even considered; one mismatch anywhere in that history rejects it outright, and swapping code to disk never hot-reloads a function you've already imported, so every candidate is measured by replaying it fresh in an isolated subprocess. By default that means re-running your real entry script from scratch and observing every call it naturally makes, so if __name__ == "__main__":-guarded code fires exactly as it would running it normally; set use_captured_inputs=True to instead replay each historical call directly from its own stored inputs, which is simpler and faster when the target is a plain function with no surrounding object state to reconstruct. Either way, each replay gets a timeout budget scaled from that function's own recorded execution time, so a candidate that hangs is marked timeout rather than left to block the run.

02 User privacy ~2 min read

Protecting sensitive data is simple with fastercode, we have a method for anonymising variables with random numbers and letters before sending code snippets to your API.  

Set privacy_mode=True and fastercode anonymizes your function before any code leaves your machine. 

Your function is parsed with Python's ast module, every function and variable name is renamed to a pseudonym. Here's the same function shown elsewhere in these docs, before and after:

python 
def sum_of_squares(values):
    total = 0
    for v in values:
        total = total + v * v
    return total
python 
def fn_d175(var_ed1f):
    var_1862 = 0
    for var_6b80 in var_ed1f:
        var_1862 = var_1862 + var_6b80 * var_6b80
    return var_1862

The real name mapping is written to .fastercode/<hash>/privacy/, and fastercode uses it to de-anonymize the LLM's response back to your real names before anything is written to refactored.json. Any keep() constraints you've registered get described to the LLM in their anonymized form too. 

Want to see exactly what would be sent before you commit to it? refactor inspect-payload path/to/script.py compute prints the full system + user prompt, the pseudonym→real-name mapping, any anonymized constraints, and a sha256 hash of the payload. 

03 Validation and results ~6 min read

Once a function is tracked and the script is executed, its inputs and outputs are logged for all calls during that execution and stored inside tracking.json. Execution time and peak memory are also recorded per call. This is a real one, from the same run as the examples below:

json 
{
  "objective": "speed",
  "constraints": {"memory": {"max_relative": 1.2}},
  "function": "sum_of_squares",
  "calls": {
    "1": {
      "execution_time_ms": 3.496,
      "peak_memory_kb": 196.68,
      "inputs": {"values": [0, 1, 2, 3, 4, "... 5000 total"]},
      "outputs": {"return": 41654167500}
    }
  }
}

Every optimised code suggestion runs the same execution and logs the inputs and outputs of each call, allowing comparison to this baseline. Comparison itself is strict equality, a candidate's output for a given call must exactly match the real recorded output for that same call. One mismatch anywhere rejects the candidate outright, regardless of the objective function metrics.

Replaying the full script

The default (use_captured_inputs=False) re-runs your real entry script fresh, in an isolated subprocess and observes every call it naturally makes, comparing that whole sequence against your function's recorded history.

Replaying from recorded inputs

Set use_captured_inputs=True to instead reconstruct and directly call your function once per historically recorded call, using that call's own stored inputs, no entry script re-run. Simpler and faster, but it only works when every recorded call's inputs/outputs are plain JSON-native values, which rules out anything that needed a class instance (like a bound method's self) to reconstruct. Recommended for simple functions.

Where results are written

Everything fastercode records is written under a single results directory. It defaults to .fastercode/ in your working directory, however you can point it anywhere you like.

Choosing the directory

Three levels, highest precedence first:

#How you set itWhat it affects
1refactor(results_dir="..."), or results_dir: in a job YAMLThat one refactor instance.
2FASTERCODE_RESULTS_DIR environment variableEvery run in that shell or process.
3nothing set, the built-in default.fastercode/, relative to the working directory.
python 
# Everything this instance records goes to build/ instead of .fastercode/
optimise = refactor(objective="speed", results_dir="build/fastercode")

The path is resolved once, when the refactor instance is constructed. 

What lands there

One folder per tracked function, named by a hash of its source and one self-contained timestamped folder per optimise() run inside it:

<results_dir>/                          .fastercode/ unless you changed it
└── <source-hash>/                     one folder per tracked function
    ├── tracking.json                  every recorded call: inputs, outputs, timings

    ├── backup_<version>_<time>.py     safety copy, written by a manual swap
    ├── privacy/
    │   └── mapping_<version>.json     pseudonym -> real name, never sent anywhere
    └── optimise_runs/
        └── run_<timestamp>/           one folder per optimise() run

pip install fastercode-ai pulls both SDKs it needs and switching provider is a one-line change. Only OpenAI and Anthropic use their own SDKs; the other six use the OpenAI protocol, so they reuse the OpenAI client against a different base URL. All you supply is the key.

python 
llm.set_credentials("openai", "${OPENAI_API_KEY}", model="gpt-4o")

LLMProvider is a small abstract base class, so adding another means registering a new provider, not redesigning anything upstream. Any API that speaks the OpenAI protocol subclasses OpenAIProvider instead, which is roughly a dozen lines.

Languages

Python is the only supported language today. More are on the roadmap, controlled through job YAML's language: field rather than the @track decorator. A decorator is Python syntax and doesn't generalize, while naming a script/function by string in YAML does.

03Tutorials

3.1 · Optimising with an LLM

1. Install fastercode from pip

shell
pip install fastercode

2. Add your API credentials

python
from fastercode import llm

llm.set_credentials("openai", "${OPENAI_API_KEY}")

${OPENAI_API_KEY} resolves from your environment at runtime, so the key itself never touches your code, a string works too, but the environment-variable form is recommended. Pass a third argument, e.g. model="gpt-4o" to override the provider's default model. 

Eight API providers are in this release: OpenAI, Anthropic, Gemini, xAI, DeepSeek, Mistral, Kimi and OpenRouter. 

3. Define a problem

python 
from fastercode import refactor

optimise = refactor(
    objective="speed",
    constraints={"memory": {"max_relative": 1.2}},
)


@optimise.track
def sum_of_squares(values):
    squares = []
    for v in values:
        squares.append(v * v)
    total = 0
    for s in squares:
        total = total + s
    return total


if __name__ == "__main__":
    sum_of_squares(list(range(5_000)))
    print("call recorded:", sum_of_squares.refactor_json_path)
    result = optimise.optimise(sum_of_squares, tries=5)

Instantiate the class 'refactor' and define the objective, either 'speed', 'loc' or 'memory'. Constraints are set with a dict, these define a subset of solutions that are relative to the reference code. In this example, constraints={"memory": {"max_relative": 1.2}} means the peak memory of new code cannot exceed 1.2x the baseline code.

Decorate the target function with @optimise.track so the package can track the execution time, loc and peak memory usage. Next, call the method 'optimise' where you want the process to commence.

4. Get results

python
from fastercode import refactor

optimise = refactor(
    objective="speed",
    constraints={"memory": {"max_relative": 1.2}},
)


@optimise.track
def sum_of_squares(values):
    return sum(v * v for v in values)

Run the script and wait. The package is running the original script, collecting statistics, submitting the targeted function to your API, hot swapping the script with new LLM suggestions and rerunning as many tries as you've declared. 

Once the process completes, you can find all copies of your target script with attempted code suggestions in the results folder (.fastercode/ by default, and configurable — see How it works) along with a pdf report and JSON files containing test results. New code is only accepted if all the collected outputs / tests match the baseline, and the objective/constraints are met. Your newly optimised code will be waiting in the original script. Don't worry, your original code is backed up in the results folder.

3.3 · Setting performance constraints

Performance constraints can be applied to any of the three objectives, speed, loc or memory. They can be applied as either relative to the baseline performance or in absolute terms. If a candidate matches the baseline outputs, meets the objective, but exceeds the constraint, it will be marked as constraint_violated and not carried forward. 

Each constraint metric takes one of two shapes:

  • max: An absolute ceiling, in the metric's own unit (ms for speed, non-blank lines for loc, KB for memory).
  • max_relative: A multiplier over this function's own recorded baseline for that metric (e.g. 1.2 = must not exceed 120% of baseline).

Decorator

Minimize speed, while constraining memory with an absolute maximum and LOC with a relative maximum:

python 
optimise = refactor(
    objective="speed",
    constraints={
        "memory": {"max": 500},        # KB - absolute ceiling
        "loc": {"max_relative": 1.5},  # multiplier over baseline - relative ceiling
    },
)

Job YAML

The same two constraints applied to the YAML job file: 

yaml 
objective: speed
constraints:
  memory:
    max: 500           # KB - absolute ceiling
  loc:
    max_relative: 1.5  # multiplier over baseline - relative ceiling

3.4 · Setting code constraints

Code constraints allow users to freeze LOC during refactors, so the LLM returns code that is unchanged in the region specified. It can also constrain variable names to eliminate the risk of a refactor erasing a variable from the function. 

python

 2    total_revenue = 0
 3    total_discount = 0
 4    for order in orders:
 5        price = order["price"]
 6        qty = order["qty"]
 7        discount = order.get("discount", 0)
 8        line_total = price * qty
 9        discount_amount = line_total * discount
10        net_total = line_total - discount_amount
11        total_revenue += net_total
12        total_discount += discount_amount
13    high_value = []
14    for order in orders:
15        if order["price"] * order["qty"] >= 100:
16            high_value.append(order)
17    low_value = []
18    for order in orders:
19        if order["price"] * order["qty"] < 100:
20            low_value.append(order)
21    average_order = total_revenue / len(orders) if orders else 0
22    return {
23        "total_revenue": total_revenue,
24        "total_discount": total_discount,
25        "average_order": average_order,
26        "high_value_count": len(high_value),
27        "low_value_count": len(low_value),
28    }

Preserving lines of code

lines=[(start, end)] preserve specific source lines exactly as they are, useful for a block that must stay a certain way regardless of what else changes around it. To make the point clearly, this example pins down lines 4-9: the for loop header through a line midway through that same loop's body. 

python 
# lines 4-9: the "for" loop header through the mid-loop discount_amount
# line - an inefficient, unfinished-looking fragment, pinned on purpose.
optimise.keep(summarize_orders, lines=[(4, 9)])
optimise.submit(summarize_orders)

Here in this example, lines 4 to 9 are chosen as the line constraints. 

python

 2    total_revenue = 0
 3    total_discount = 0
 4    for order in orders:
 5        price = order["price"]
 6        qty = order["qty"]

 8        line_total = price * qty

10        net_total = line_total - discount_amount
11        total_revenue += net_total
12        total_discount += discount_amount
13    high_value = [o for o in orders if o["price"] * o["qty"] >= 100]
14    low_value = [o for o in orders if o["price"] * o["qty"] < 100]
15    average_order = total_revenue / len(orders) if orders else 0
16    return {
17        "total_revenue": total_revenue,
18        "total_discount": total_discount,

21        "low_value_count": len(low_value),
22    }

This code snippet shows the result when minimising LOC is chosen as the objective and lines 4 to 9 are selected as the code constraints. The solution reduces LOC from 28 in the original to 22 in the optimised output, while retaining lines 4 to 9 as they were (which enforces the inefficient for loop). 

The YAML job equivalent:

yaml 
targets:
  - name: summarize_orders
    keep:
      lines: [[4, 9]]

Preserving variable names

variables=[...] preserves specific variable names, useful when downstream tooling, logging, or a reviewer's mental model depends on a name staying put, even if the LLM would otherwise rename it.

python 
optimise.keep(summarize_orders, variables=["net_total"])
optimise.submit(summarize_orders)

In this example the variable 'net_total' is preserved in the refactor, originally appearing on line 10, now appearing on line 7. You can also see a new variable was introduced underneath on line 8 called 'net_totals' which is used to calculate total revenue on line 10. 

python 
 1def summarize_orders(orders):
 2    net_totals = []
 3    total_discount = 0
 4    for order in orders:
 5        line_total = order["price"] * order["qty"]
 6        discount_amount = line_total * order.get("discount", 0)
 7        net_total = line_total - discount_amount
 8        net_totals.append(net_total)
 9        total_discount += discount_amount
10    total_revenue = sum(net_totals)
11    high_value = [o for o in orders if o["price"] * o["qty"] >= 100]
12    low_value = [o for o in orders if o["price"] * o["qty"] < 100]
13    average_order = total_revenue / len(orders) if orders else 0
14    return {
15        "total_revenue": total_revenue,
16        "total_discount": total_discount,
17        "average_order": average_order,
18        "high_value_count": len(high_value),
19        "low_value_count": len(low_value),
20    }

The job YAML equivalent:

yaml 
targets:
  - name: summarize_orders
    keep:
      variables: ["net_total"]

3.5 · Using privacy mode

privacy_mode defaults to True, the baseline is anonymized. Every identifier in the function you're sending gets replaced with a meaningless pseudonym before anything leaves your machine, the real names never reach the LLM at all. Pass privacy_mode=False if you want real identifiers sent instead (e.g. for a private/self-hosted model where anonymization buys you nothing):

python 
# privacy_mode defaults to True - identifiers are anonymized before any
# code reaches the LLM. Pass False to send real names instead.
optimise = refactor(objective="speed", privacy_mode=False)

Before:

python 
def sum_of_squares(values):
    total = 0
    for v in values:
        total = total + v * v
    return total

After:

3.6 · Iterative vs. independent feedback

Users are able to select optimising the code with either an iterative method or an independent method. The independent methodsends an identical prompt to the LLM every try, no memory of previous attempts. The iterative method sends a different prompt each try. It always states the metric to beat and from the second try onward it appends the previous attempt metrics and pass or fail conditions. Every earlier entry stays in the prompt for the rest of the run, so the accumulated history keeps growing. 

Decorator

python 
# independent: every try restarts from the untouched original and gets
# the exact same prompt - true i.i.d. sampling, no memory between tries.
result = optimise.optimise(sum_of_squares, tries=3, mode="independent")

# iterative (the default): each try builds on the current best, and the
# prompt grows every try with what already happened in this run.
result = optimise.optimise(sum_of_squares, tries=3, mode="iterative")

This is an example of the accumulated history in the iterative method: 

output 
Current best execution time (ms): 0.19739987328648567. Beat this.

Attempt 1 - REJECTED (produced incorrect output):
def sum_of_squares(values):
    return sum(v * v for v in values) + 1

Attempt 2 - ACCEPTED (new best execution time (ms) = 0.18109986558556557):
def sum_of_squares(values):
    total = 0
    for v in values:
        for _ in range(1):
            total = total + v * v
    return total

This whole block is added to the user prompt, appended after the objective's usual instructions. The system prompt for the objective never changes between tries. In mode="independent", no feedback section is added at all, every try's prompt is identical.

Job YAML

The job YAML equivalent:

yaml 
post_run:
  - action: optimise
    target: sum_of_squares
    tries: 3
    mode: iterative      # or independent
